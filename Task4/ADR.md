### <a name="_qmphm5d6rvi3"></a>**Решение**
Архитектура системы разделена на два ключевых контейнера:

rates-service — отвечает за приём и агрегацию ставок;
rates-exporter — занимается формированием и отправкой файлов ставок.

Получение ставок:<br>
Сотрудник кол-центра работает через CRM-систему, которая обращается к rates-service по REST API. Сервис агрегирует данные и записывает актуальные ставки в Redis.

Хранение данных: Redis используется как общее хранилище ставок. Это позволяет нескольким компонентам иметь доступ к одинаковым данным и обеспечивает масштабируемость.

Формирование файлов:<r>
rates-exporter запускается по событию обновления ставок от rates-service, забирает ставки из Redis, формирует файл (CSV) и отправляет его в систему партнёрского колл-центра, откуда с ним работают сотрудники.

Масштабируемость:
rates-service масштабируется горизонтально для обслуживания большого количества запросов. Возможно размещение дополнительного балансировщика для распределения запросов.
rates-exporter может работать как отдельный экземпляр (или CronJob), не блокируя основной сервис.

Redis обеспечивает консистентность данных между контейнерами.
### <a name="_bjrr7veeh80c"></a>**Альтернативы**

#### 1. **Монолитный подход (всё в одном сервисе)**

Можно было реализовать всю логику в рамках одного контейнера:

* Один сервис принимает ставки, кэширует, формирует и выгружает файлы.

**Плюсы:**

* Проще реализовать и развернуть.
* Нет межсервисной интеграции.
* Меньше инфраструктурных компонентов.

**Минусы:**

* Плохая масштабируемость (нельзя независимо масштабировать обработку API и выгрузку).
* Смешение ответственности (API, кэш, генерация файлов).
* Повышенный риск деградации: тяжёлая выгрузка может повлиять на скорость API.

#### 2. **Запись ставок напрямую в БД**

Вместо Redis можно было использовать обычную СУБД (PostgreSQL и т.д.).

**Плюсы:**

* Простая реализация, стандартные инструменты для работы.
* Привычная модель консистентности.

**Минусы:**

* Снижение производительности при высоких нагрузках.
* Больше накладных расходов на формирование выгрузки (JOIN, фильтрация).
* Потенциально избыточная долговременная история (если она не нужна).


**Недостатки, ограничения, риски**

1) Частые триггеры экспорта при обновлении ставок rates-exporter запускается по событию от rates-service.
При частом обновлении ставок (например, при пакетной загрузке или пиковой активности) это может привести к избыточным запускам и загрузке инфраструктуры.
Рекомендация: предусмотреть таймаут или rate limiter, чтобы запуск происходил не чаще заданного интервала.
2) Для горизонтального масштабирования rates-service потребуется:<br>
либо установка балансировщика (если сервис вызывается напрямую),
либо интеграция с API Gateway, через который CRM направляет запросы.
Это добавляет зависимость от инфраструктуры и требует настройки маршрутизации.
3) Между записью в Redis и запуском экспорта может возникать рассинхронизация, особенно при сбоях.
Рекомендация: предусмотреть повторные попытки или фоновую проверку актуальности данных перед выгрузкой.
4) Увеличение количества компонентов<br>
Разделение на rates-service и rates-exporter повышает модульность и масштабируемость, но требует:
отдельной поддержки,
мониторинга,
логирования и алертинга на каждый сервис.
